# Journal - 2026-11-23

## Problem: stopped-out positions stuck as "DB Only" (Fri 2026-11-20)

Many stop losses filled on Friday. During the day the dashboard showed those positions
as "DB Only" (gone from IBKR, still OPEN in the DB) and they did not appear under
Closed Positions. They were closed later without intervention.

### Root cause

- The only code that closes positions is the fill handler in `connection_manager.py`.
- The connection manager connects as **clientId 50**; the TP/SL orders are placed by the
  trader as **clientId 0**.
- IBKR pushes live `execDetails` only to the clientId that placed the order, or to the
  gateway's *Master API client ID*, which was not set (`OverrideTwsMasterClientID=` blank).
  So the live fill callback never fired for TP/SL fills.
- The only other path was the "today's executions" scan on (re)connect. `reqExecutions`
  returns fills from all clients, so the nightly gateway restart (AUTO_RESTART_TIME
  11:45 PM ET) closed Friday's positions that evening. A reconnect after midnight would
  have missed them (filter = today only).
- Misconception in `config.py`: clientId 0 is NOT automatically the master client.
- Why not clientId 0 everywhere: IBKR allows one connection per clientId; the persistent
  connection manager would block the trader's 09:35 connection.

### Fix (branch `worktree-fix-fill-detection`, not yet deployed)

1. `connection_manager.py`
   - Re-scan executions every 60 s (not only on connect); lookback from start of yesterday.
   - One shared `_handle_fill()` for the live event and the scan.
   - Exec ID is remembered only after the DB write succeeds (transient DB errors retried).
   - Guard: a fill only closes a position whose `entry_time` is before the fill, so a
     replayed old fill (after a restart) cannot close a newer position on the same contract.
2. `docker/ibc/config.ini`: `OverrideTwsMasterClientID=50` so live fills reach the connection
   manager. Only applied when the **gateway** restarts (deploy restarts only `trading-bot`),
   and needs checking that the gnzsnz image honours the mounted config.ini.
